# 食事選択サポートアプリ "My Cook Concierge"

## 1. サービス概要

- **このサービスはどんなサービスか**
  「今日の食べたいものが考えても思いつかない」という瞬間に、いくつかの質問にパパッと答えるだけで、お酒のおつまみやお菓子も含めた今の気分にぴったりの料理をジャンルごとに提案してくれる食事決定サポートアプリです。
- **誰の、どんな課題を、どう解決するか**
  今日何を食べようか悩んで時間を無駄にしている人の、「決まらない・探すのがめんどくさい」という課題を、文字入力不要な性格診断スタイルの質問と、ユーザー自身が調整できる質問数設定によって、手軽かつスピーディーに解決します。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

- **いつ**：平日の夜や休日など、週に何度か訪れる「食事を決めるタイミング」
- **どんな状況で**：お腹は空いているのに「これが食べたい」という具体的なメニューが全く思い浮かばず、スマホのグルメアプリや冷蔵庫の前で、食べたいものを探して迷走しているとき
- **どんな気持ちになったか**：
  日々の食事という毎日の当たり前の選択のはずなのに、食べたいものが見つからず苦労することに強いストレスを感じた。探せば探すほど時間が過ぎていき、「悩む時間が多ければ多いほど、人生の貴重な時間をただ無駄に消費しているだけではないか」という強い焦りと、もったいなさ、退屈さを抱いた。

### 2-2. なぜそれが「気になった」のか

- **効率性と時間を大切にする価値観**：
  私は、日々の生活の中での「生産性のない無駄な時間」を減らし、時間を有意義に使いたいという価値観を持っています。食事自体は楽しみなものであるべきなのに、「何にするか決めるだけ」のフェーズで思考がスタックし、時間を浪費してしまう状況に対して、人一倍強い違和感とストレスを覚えたためです。
- **日常の小さな摩擦への気づき**：
  「食事迷子」になることは多くの人が「よくあること」として諦めがちですが、毎日、あるいは一生続く選択だからこそ、この小さな意思決定のコスト（決断疲れ）を解消することには大きな価値があると確信したからです。

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

食事のタイミングで「食べたいもの」がパッと思い浮かばず、スマホのグルメアプリやレビューサイトをダラダラと見続けてしまい、決めるまでに多くの時間を浪費してしまうこと。

### 3-2. 本当に解決したい課題は何か

- **なぜ決めるのに時間がかかると困るのか？（なぜ①）**
  → 毎日の生活の中にある、貴重な自由時間が失われてしまうから。
- **なぜ毎日の貴重な時間が失われると困るのか？（なぜ②）**
  → その時間があれば、映画を観たり、趣味を楽しんだり、心からリラックスしたりできるはずの「自分のための時間」がなくなってしまうから。
- **なぜ自分の時間がなくなると困るのか？（なぜ③）**
  → 本来リフレッシュできるはずの時間に、スマホの画面を凝視し続けて目が疲れ、頭痛が起きたり、何も決まらない焦りからイライラして精神的なストレスを抱えてしまうから。

**→ 本当に解決したい課題：**
日常の「何を食べよう」という些細な選択の迷いによって、本来得られるはずの「自分の時間」と「心身のゆとり」が奪われ、ストレスと疲れを引き起こしていること。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

「社会人として働き、日々の業務や責任に追われながら、食事の選択にストレスを感じている現役のビジネスパーソン」

- **年齢設定：**
  - **年齢：** 20代〜50代の働く社会人世代
  - **理由：** 高齢者層は食事の量や選択への関心が落ち着いている傾向がありますが、20代から50代の現役社会人は「せっかくなら美味しいものを食べてエネルギーを補給したい」という欲求が高い世代です。しかし同時に、若手からベテラン、管理職に至るまで、日々の仕事による脳の疲労（決断疲れ）が最も大きい年代です。スマホで食事を探すスキルを持ちつつも、「選ぶ気力が出ない」というジレンマを一番抱えている年齢層であるため、本アプリが広く必要とされると考えたからです。

- **生活・状況設定：**
  - **生活・状況：** 平日は残業が多く、帰宅はいつも夜20時以降になる一人暮らしの社会人。仕事で脳も体も疲れ切っているため、自炊をする気力は残っておらず、外食やテイクアウト、コンビニなどで手軽に済ませたいと考えている。しかし、お腹は空いているのに「何が食べたいか」の具体的なメニューが疲労のせいで全く思い浮かばず、毎日同じものを選んで飽きるか、スマホを見ながら迷走してしまう状況。
  - **理由：** 疲労による思考停止（決断疲れ）が起きている場面において、アプリがユーザーの代わりに選択肢をスマートに提示、または絞り込んであげることで、迷うエネルギーを一切使わずに「今、満足できる食事」へ直感的にたどり着けるようにします。

- **環境設定：**
  - **環境：** スマホの中に、Instagram、TikTok、グルメサイト、出前アプリなど、食に関する情報収集ツールが大量に入っている環境。選択肢や情報が世の中に溢れかえりすぎている。
  - **理由：** 「情報が多すぎて逆に選べない（選択のパラドックス）」という現代特有のハードルを、アプリが情報をあえて「制限」したり、ノイズをカットしてシンプルに推薦したりする仕組みによって解消します。情報過多による決断疲れからユーザーを解放します。

### 4-2. 自分とユーザーの距離

- **ターゲットとの距離：** 自分自身
- **理由：**
  私自身が週に何度も「食べたいものが見つからない」という状況に陥り、貴重な時間を無駄にしてイライラや疲労を感じている当事者だからです。自分自身が心から「今すぐ欲しい」と思えるサービスを追求することが、同じように日々社会で働く人たちのリアルな課題を解決することに直結すると確信しています。

### 4-3. 実際に使われる可能性について(需要・存在確認)

- **まず最初に使ってくれそうな人は誰か？**
  → 「今日、何を食べようかな」とリアルタイムで悩んでいる人。
- **その人は、どんな場面でこのアプリを思い出すか？**
  → 自分なりにメニューを考えてみたものの、どうしても具体的な食べたいものが頭に思い浮かばないとき。
- **今の生活の中で、代わりに使っているものは何か？**
  → クラシルやクックパッドなどのレシピアプリ、またはChatGPTなどの生成AIサービス。
- **それらを置き換えてまで使う理由はあるか？**
  → AIに「おすすめの晩御飯は？」と聞いても、選択肢が広すぎて結局決まらないことが多く、レシピアプリは大量のレシピから自分で「探す」という能動的な行動が必要なため、疲れているときはその作業自体が非常に面倒です。
  本アプリは、文字を入力する手間の代わりに、**「性格診断のように、提示される質問にパパッと直感的に答えるだけ」**でピンポイントに食事を提案してくれます。この「圧倒的な楽さ」と「思考停止したままでいい快適さ」があるため、既存ツールを置き換えてまで使う明確な理由になります。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)

- **どんな場面・困りごとがきっかけで、このサービスを知る・思い出すか**
  → お腹が空いているのに何を食べたいか分からず、スマホの画面をダラダラ眺めて「また今日も時間を無駄にしてしまった…」と決断疲れを起こした瞬間。ネットやSNSで「質問に答えるだけでご飯が決まる診断ツール」として認知し、思い出すきっかけになります。
- **最初の一歩（登録・導入）で、ユーザーは何をする必要があるか**
  → ゲストユーザーとして登録不要ですぐに利用することも可能ですが、アカウント登録（ログイン）をすることで、気に入った料理を「お気に入り保存」できるようになります。
- **利用を続ける理由は何か？（習慣・必要性・価値）**
  → 使うたびに「自分で探さなくていい」「質問に答えるだけでピタッと食べたいものが決まる」という成功体験が積み重なるためです。お気に入りしたメニューがストックされることで、自分だけの「迷った時の食事リスト」が完成し、利用価値がさらに高まります。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

#### 競合①：AIパーソナル診断フードレコメンドアプリ（FOODERS など）
- **どんなことができるか**：AIを搭載し、天気や体調、食の好みに関するいくつかの質問に答えることで、AIがパーソナライズされた一品を提案してくれるアプリ。

#### 競合②：直感スワイプ式食事決定アプリ（今日、何食べる？ / food-swipe など）
- **どんなことができるか**：料理カードを左右に直感的にスワイプ（仕分け）していくことで、考える時間をゼロに近づけて食事を即決できるWebアプリ。

#### 競合③：自動献立生成・買い出し管理アプリ（me:new［ミーニュー］など）
- **どんなことができるか**：最長1週間分の献立を自動で作成し、それに連動した買い物リストまで一括生成してくれる、主に家庭・主婦向けの効率化アプリ。

### 5-2. それでも自分が作りたい理由

既存のサービスは、手軽に「今日の1品」を決めたい人の心理や、お酒・お菓子といった幅広い食事シーンのニーズとズレがあると感じたからです。

- **AI診断アプリ（FOODERS等）への不満・ズレ**：
  質問数が固定で多く、答えるのが手間に感じることがあります。本アプリでは、質問の細かさ（質問数）をユーザー自身で設定できるようにしたいです。また、既存アプリは「主食・主菜」の提案に偏っていますが、私のアプリでは「おつまみ」「お酒」「お菓子」といった、あらゆる食の選択肢も案内できるようにしたいと考えました。
- **スワイプ式アプリ（food-swipe等）への不満・ズレ**：
  料理カードを見て仕分ける行為は、結局のところクックパッドやクラシルで大量のレシピから検索している作業と本質的に変わらず、探す手間や迷いが発生してしまいます。
- **献立自動生成アプリ（me:new等）への不満・ズレ**：
  これらは数日分の献立をきっちりと計画するためのものであり、システムが重すぎます。「毎日悩むわけではないけれど、今日だけ、今この瞬間だけ食べたいものが思いつかない」というときに、手軽に1品だけ調べたいニーズに合っていません。

### 5-3. 差別化を「体験価値」で表現する

私のアプリは、**【今日の食べたいものが考えても思いつかない人】**の、**【今この瞬間の気分に合う1品（ご飯、おつまみ、お菓子など何でも）を手軽に決めたい瞬間】**を一番助けるアプリです。

- **私のアプリの差別化ポイント：**
  ユーザーが自分の状況に合わせて質問の細かさを選べる柔軟性と、食事だけでなく「お酒・おつまみ・お菓子」まで網羅した、手軽な1品決定体験。
  さらに、気に入った提案を自分専用に保存できる「お気に入り機能」によって、使えば使うほど迷う時間を削減できる体験価値を提供します。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- **行動の変化**：
  「何を食べよう」とレシピサイトをダラダラ検索して時間を無駄にすることがなくなり、質問に答えてすぐに「これにしよう」と食事の準備や購入に移れるようになる。
- **気持ちの変化**：
  「食べたいものが見つからない」という日々の小さなモヤモヤやイライラが解消され、食事の時間自体をすっきりと楽しめるようになる。
- **考え方の変化**：
  メニューを「考えても思いつかない」ときは、自分で無理に探すのではなく、アプリにパッと聞いて心地よく決めるのが一番効率的だと思えるようになる。

### 6-2. 価値を一文で表す

このサービスは、今日の食べたいものが考えても思いつかない人が、質問に答えるだけで、お酒のおつまみやお菓子も含めた今の気分にぴったりの料理を決められるようになるサービスです。

## 7. このアプリで実現すること

### MVPで作る機能
*   **ユーザー登録・ログイン機能**：提案された料理をお気に入り保存するための認証機能（Rails 8標準の認証システムを利用）
*   **質問数（細かさ）の設定機能**：ユーザーが診断を始める前に、自分で質問の数（例：サクッと3問、じっくり5問など）を設定できる機能
*   **質問回答機能**：設定された数に応じて、画面に提示される質問（気分やシチュエーションなど）にタップで答えていく機能
*   **おすすめ料理のジャンル別表示機能**：回答完了後、今の気分にマッチしたおすすめの料理（おつまみ、お菓子、主食など）が、ジャンルごとにいくつか一覧で提案・表示される機能
*   **お気に入り保存機能**：提案された料理をユーザーごとに保存できる機能

### 本リリースで作る機能
*   **外部サイトへの誘導機能**：提案された料理のレシピサイトや、デリバリー・グルメサイトへのリンクボタンを設置し、次の行動へスムーズに繋げられるようにする
*   **料理写真の挿入**：テキストだけでなく、視覚的にも「食べたい！」と思わせる魅力的な料理画像を各メニューに追加する
*   **みんなの迷った料理ランキング機能**：ユーザー全体の診断ログをバックグラウンドで集計し、「みんなが何にするか一番迷っている料理ランキング」を表示する機能
*   **UI/UXの改善**：アニメーションの追加など、より直感的にパパッと操作できる画面デザインへの全体的なブラッシュアップ

## 8. このアプリの懸念点とその対策

### 懸念点①

- **何が問題になりそうか：**
  ユーザーが「答えていて楽しい、納得感がある」と思えるような的確な質問内容を設計すること、および、おつまみやお菓子まで含めた大量の「料理データ」をリレーショナルデータベース（PostgreSQL）に矛盾なくマッピングし、効率的に管理する点。
- **なぜそう思うか：**
  質問が退屈だったり的外れだったりすると、ユーザーは途中で飽きて離脱してしまいます。また、提案される料理のカテゴリやタグ（おつまみ、ガッツリ等）のDB設計が不適切だと、気分と一致しない料理が提案され、アプリとしての信頼性が薄れてしまうからです。
- **そのために考えている対策：**
  まずは身近な定番メニューやおつまみ、お菓子に絞り、シンプルなテーブル設計（ユーザー、料理、質問、お気に入り）でスモールスタートします。質問設計に関しては、既存の心理テスト等のフローを参考にパターン化し、RailsのActiveRecordを用いてタグやカテゴリを正確に抽出できるクエリを構築します。データ投入はシードファイル（`db/seeds.rb`）を活用して一括管理し、初期開発を効率化します。

## 9. 今後の展開・発展の方向性

### 今考えている発展案

- **機能追加の方向性：**
  初期段階では、ログイン機能と基本的なお気に入り保存機能の実装に集中します。将来的には、SNS（Xなど）を通じて「こんなおつまみも追加してほしい」といった実際のユーザーのリアルなリクエストを取り入れ、料理マスターのデータを拡充します。
- **データが溜まると何ができる？：**
  ユーザーが増え、診断のログやお気に入りのデータがPostgreSQLに蓄積された段階で、バックグラウンド処理（ActiveJob / whenever）をフル活用します。毎週定期的にデータを自動集計し、「迷ったときはこれを選べば間違いない！今週の人気メニューランキング」を生成してトップページに掲載するなど、集計データに基づいたエンタメ性の高い提案機能へ発展させていきたいと考えています。

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

- **フレームワーク：** Ruby on Rails 8.0 (Ruby 3.3 / TypeScript)
- **DB：** PostgreSQL
- **デプロイ先：** Render
- **主なライブラリ・ツール：** Tailwind CSS, Docker, RSpec, Resend, whenever (本リリースで実装)

### 10-2. 技術選定の比較検討

使用する技術の選定にあたり、スクール環境の活用、将来の展望、および開発スピードを考慮して以下の通り比較検討を行いました。

#### バックエンド・データベース技術の比較

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| **Ruby on Rails 8.0 + PostgreSQL** | **採用** | スクールのカリキュラム（Render/Docker）との互換性が最も高く、信頼性と拡張性に優れているため。Rails 8.0から標準搭載された認証ジェネレータを使用することで、外部ライブラリに頼らずに軽量で安全なログイン機能を迅速に実装できる。また、将来的なランキング集計やデータの定期処理に強力なORマッパー（ActiveRecord）とPostgreSQLが不可欠であると判断したため。 |
| Next.js + JSONファイル管理 | 不採用 | 当初は最速リリースのためファイル管理を検討したが、スクールの卒業要件である「ER図の提出」を満たす必要があり、またユーザー個別のお気に入り保存機能や本リリースでのランキング機能のデータ集計には、堅牢なリレーショナルデータベース（RDB）の導入が最適であると判断したため。 |
| Node.js (Express) | 不採用 | 認証機能、バックグラウンドジョブ、テスト環境、O/Rマッパーなどをすべてゼロから選定・構築する必要があり、Rails 8.0に比べてMVP完成までの開発スピードが大幅に落ちるため。 |

- **今回チャレンジしたい点：**
  Rails 8.0の新しい標準認証機能をキャッチアップし、セキュアでシンプルなログイン・お気に入り機能を構築すること。コンポーネントを意識したTailwind CSSによる美しいUI/UXの実装、およびDockerを用いたクリーンな開発環境の維持。
- **不安な点：**
  おつまみやお菓子など多岐にわたる料理データを、ユーザーの選んだ質問数や回答条件（タグ）に合わせて正確かつ高速にデータベースから引き出すための、クエリ（ActiveRecord）の設計部分。

### 10-3. キャッチアップ不足の懸念

キャッチアップ不足の段階では以下の懸念点があります。
1. **完成までのハードルが高い**
使用する言語やフレームワークが異なるため、キャッチアップにかかる時間は個人差があるものの、一定の時間を要することが予想されます。
2. **Issueの見積もりが難しい**
「どこまで理解していて、何が分からないのか」「調査にかかる時間」などが不明瞭な場合、開発期間内に完了することが難しくなってしまいます。

例えば、最近注目されているRails 8の最新機能について。
基本的なCRUD機能や認証周りはMVPとして実装しますが、`Sidekiq` や `whenever` を用いた高度なバックグラウンドジョブ処理に関しては、**本リリース後に組み込む方向で検討**するのが良いかと考えています。
まずは基本機能の実装とデプロイまでのキャッチアップを行い、アプリが安定して稼働する技術的な検証をした上で、段階的に新技術を組み込むかどうかを判断する形が理想と考えます。
